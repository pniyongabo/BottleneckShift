# BottleneckShift Milestone 1: RTX A4000 concurrency experiment

## Result

Increasing maximum client concurrency from 1 to 8 increased output throughput approximately 6.6× while increasing median request latency approximately 16%. Both execution orders show this tradeoff. This is a successful first end-to-end experiment, with a cache-state limitation that prevents attributing the full effect exclusively to concurrency or identifying a hardware bottleneck.

## Interpretation and limitations

- The throughput gain and latency increase appear in both directions. Two concurrency settings do not establish a saturation point. No controlled GPU, CPU, or network contention intervention was performed.
- **Prefix caching is an observed source of history dependence.** Both server logs explicitly show `enable_prefix_caching=True`. Logged cache-hit rates rise from 0% to the last reported 75.4% forward and 78.1% reverse. The benchmark reuses seed 2027 while retaining the server across repetitions. Reused prompts are therefore a plausible source of cross-run cache reuse, but the archive does not establish identical prompt token sequences or per-request cache hits.
- **Reverse C8 repetition 1 is retained.** Its TTFT median is 51.55 ms, compared with 32.15 and 36.59 ms in repetitions 2 and 3; output throughput is 1,568 versus 1,630 and 1,635 tokens/s. Cache state and warm-up are hypotheses, not proven explanations. The first eight requests in that repetition have TTFT around 41–43 ms, so the higher run median is not explained solely by the first batch.
- Ten serial warm-up requests do not explicitly warm the concurrency-8 workload. Reversing order helps expose history effects but does not remove them.
- The server logs resolve model and tokenizer revisions as `main`; the immutable model revision is not pinned in the config. They also warn that model generation-config defaults override some vLLM sampling defaults. Effective request-level settings should be captured explicitly in the next protocol.
- E2E latency is reconstructed as TTFT plus summed inter-token intervals; TPOT uses the same sum divided by 127. Some requests have fewer than 127 recorded intervals despite reporting 128 output tokens, which can occur with streamed chunks containing multiple tokens. This is not evidence of lost output, but recorded ITLs should not be interpreted as one hardware decode-step measurement per token.
- Logs contain shutdown-time force-kill warnings after completed runs. No `ERROR` lines were found in the two measured server logs; request results passed validation. Three repetitions per condition and one VM allocation support descriptive findings, not broad statistical generalization.

## Reproduction notes

Use the archived source, requirements, configs, setup scripts and dependency manifests. The original Hyperstack image shipped R570, which could not initialize the installed CUDA 13 PyTorch runtime. A full graphics-driver upgrade failed during package unpacking. On a fresh VM, the successful compute-only installation was:

```bash
sudo apt-get install -y --no-install-recommends \
  "linux-headers-$(uname -r)" \
  nvidia-headless-580-open nvidia-utils-580 \
  nvidia-fabricmanager-570- libnvidia-gl-570-
sudo reboot
```

This command records the successful approach on this image; future package resolution must be checked. After reboot, NVIDIA-SMI, persistence service, a PyTorch CUDA computation, five repository tests, both preflights, and a disposable inference run passed. The archive’s `step9.sh` records the measured-pair invocation.

## Recommended next experiment

Preserve this pair unchanged. Create a new reviewed protocol and series that explicitly controls prefix caching (disable it for a concurrency-only baseline, or define and validate a deliberate cache-warming policy). Warm both concurrency levels, pin the model/tokenizer revision and effective sampling settings, and record those choices in the manifest. Repeat the forward/reverse pair; keep the original results as the initial cache-enabled experiment. Do not silently apply new settings to this series.

The runner now supports these controls for a future config, but no follow-up config is declared reviewed here: set `server.enable_prefix_caching`, immutable `server.model_revision` and `server.tokenizer_revision`, a `[sampling]` table, and `execution.warmup_concurrencies = [1, 8]`. Review the resolved values before collecting a new series.
