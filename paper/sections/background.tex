\section{Background}
\label{sec:background}

\paragraph{Phases and steps.}
vLLM runs in \emph{engine steps}: each step, the scheduler picks the tokens to process
and the model runs one forward pass over them. A request waits in a \emph{queue}; its
\emph{prefill} then processes the prompt and produces the first output token, and its
\emph{decode} produces each remaining token, one per step. With chunked prefill
\citep{agrawal2024sarathiserve}, a long prompt is split across steps, so one step can
carry both decode tokens and prompt chunks. vLLM 0.29.0 enables asynchronous
scheduling by default in our configuration: it schedules step $n{+}1$ before it
processes step $n$'s results.

\paragraph{Token budget.}
The \emph{token budget} $B$ (\texttt{max\_num\_batched\_tokens}) is the most tokens one
step may process, counting one per decoding request and every prompt token in the
step's chunks. vLLM's default for its API server on GPUs under 70\,GB, as here, is
2048. The scheduler fills each step with running requests first and then with waiting
prompts, until the budget is used. A step that carries a large chunk takes about as
long as a prefill, and every request decoding in it waits. vLLM's documentation says
smaller budgets give better ITL and larger ones better TTFT and throughput
\citep{vllmdocsoptimization}.

\paragraph{Metrics.}
We use the definitions of vLLM's benchmark. TTFT runs from sending a request to its
first streamed output, and E2E to its last. Inter-token latency (ITL) is each gap
between consecutive streamed outputs of a request, usually one token each; time per
output token (TPOT) is a request's average gap, $(\mathrm{E2E}-\mathrm{TTFT})/(n-1)$
for $n$ output tokens. We report ITL p50 and p99, because averages hide jitter
\citep{agrawal2024etalon}. The benchmark pools the gaps of all requests in a run, and
one step produces a gap for every request decoding in it, so p99 reflects a run's
slowest few steps; a mean ITL nearly equals the mean TPOT. The \emph{share of latency
before the first token} is $\sum \mathrm{TTFT} / \sum \mathrm{E2E}$ over a run.
vLLM's server histograms split each request into queue, prefill (first scheduled to
first token), and decode (first token to last) time.
