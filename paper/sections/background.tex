\section{Background}
\label{sec:background}

A request in vLLM waits in a \emph{queue}, has its prompt processed (\emph{prefill}),
and then generates its output one token per engine step (\emph{decode}).
Iteration-level scheduling admits and retires requests between steps
\citep{yu2022orca}, and paged KV-cache management keeps memory for many concurrent
requests \citep{kwon2023vllm}. With \emph{chunked prefill}, a long prompt is split
across several steps \citep{agrawal2024sarathiserve}. vLLM's scheduler fills each step
first with its running requests (one token per decoding request, or the next chunk
of a prompt in progress) and then with waiting prompts, up to the \emph{token budget} $B$
(\texttt{max\_num\_batched\_tokens}). A step that carries a large chunk takes about as
long as a prefill, and every request decoding in that step waits for it. vLLM's
documentation says smaller budgets give better inter-token latency, and larger ones
better TTFT and throughput \citep{vllmdocsoptimization}.

We use the client-side metrics of vLLM's benchmark. Inter-token latency (ITL) is the
gap between consecutive streamed tokens of one request, and E2E is the whole request's
latency. The \emph{share of latency before the first token} is $\sum \mathrm{TTFT} /
\sum \mathrm{E2E}$ over a run's requests. We report the ITL median (p50) and 99th
percentile (p99), because averages hide jitter \citep{agrawal2024etalon} and tails
matter at scale \citep{dean2013tail}. The benchmark pools the gaps of all requests in a
run, and one engine step produces a gap for every request it carries, so a run's ITL
p99 reflects its slowest few steps.
